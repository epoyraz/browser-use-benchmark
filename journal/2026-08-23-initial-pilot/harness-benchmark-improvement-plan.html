What the first run taught us—and how to make the benchmark credible

A practical diagnosis of the crossed results, the new task-wide CAPTCHA exclusion rule, runtime variance, and the next experimental design.

Based on pilot harness-pilot-20260823-t001 Raw artifacts preserved Task-wide CAPTCHA exclusion implemented Broader rerun still required

Reflection

The benchmark is mechanically sound but experimentally under-specified.

The runner did the hard engineering work well: isolation, provenance, model selection, evidence capture, judging, and teardown all held. The paired schedule exposed a complete second-arm order effect. Under the corrected policy, one CAPTCHA observation excludes that task across every agent, harness, and repetition. Since the pilot selected only one task, its official result is now zero scored tasks—not a tie and not a ranking.

Diagnosis, with confidence

High
Order/site-state confound. Evidence: 2/2 first arms passed with no CAPTCHA; 2/2 second arms encountered CAPTCHA. Harness labels were balanced across those positions.
High
Raw cell scoring conflates capability and environment. Luna recognized Claude/v1’s answer as correct but returned a raw failure solely because the prompt mandated failure after any CAPTCHA. Task-wide exclusion prevents that verdict from affecting the comparison.
High
Sample size cannot support comparison. One task × one repeat provides no estimate of model or website variance and no confidence interval.
Medium
Latency is confounded. Codex/v2 exited early at 70.4 seconds; Claude/v1 spent 391.6 seconds recovering. Neither value estimates steady-state harness speed.
Medium
Headless/local browsing may increase blocking risk. Plausible, but this run did not include a headful or isolated-egress control, so it is not established.

Separate raw evidence from the scored task set

P0

Raw audit verdict

Keep each judge pass/fail verdict and evidence unchanged so the run remains reproducible. Raw cell verdicts are never the headline comparison after an exclusion.

P0

Task-wide CAPTCHA exclusion

If any cell reaches CAPTCHA or human verification, exclude the whole task across every agent, harness, and repetition—including otherwise clean cells and timing deltas.

P1

Answer correctness

Record whether the final answer itself is correct, independently of environment policy. This captures cases like Claude/v1 without rewarding CAPTCHA interaction.

Adjustments implemented after the pilot

  • Added explicit Codex, Claude, and judge effort options.
  • Applied effort to both contestant and judge commands.
  • Recorded effort in manifests and judgement artifacts.
  • This run used Terra high and Luna max exactly as requested.
Implemented

Validity-aware, task-wide reporting

  • Added task-level CAPTCHA detection and an explicit exclusion list.
  • Excluded every affected task cell and paired timing delta from scoring.
  • Added within-pair order diagnostics and CAPTCHA rates.
  • Added judge failure reasons to the Markdown report.
  • Added warnings for low repeats, blockers, and strong order effects.
Implemented

Consistent CAPTCHA behavior

  • Agents must now treat CAPTCHA/human verification as a blocker.
  • They save one screenshot, stop interacting, and report the wall.
  • This prevents one model from spending minutes on a task that cannot enter the scored set.

Further changes before a reportable comparison

P0 · required

Pre-declared reserve-task pool

Select reserve tasks before execution. If CAPTCHA excludes a primary task, report the exclusion and fill the sample from the next reserve in a fresh run block, without choosing replacements based on harness outcomes.

P0 · required

Minimum replication gate

Require at least three repetitions before any harness claim. Alternate or randomize order within each task/repetition and report exact paired confidence intervals.

P0 · required

Task viability metadata

Manually label read-only, browser-state-only, download, authentication, and external-side-effect tasks. Runtime keyword screens are not enough.

P1 · anti-bot

Separate browser modes

Keep local-headless results distinct from headful or isolated cloud-browser results. If isolated egress is used, treat it as a fixed experimental axis—never mix modes in one aggregate.

P1 · judging

Use deterministic graders where possible

Exact-list, numeric, and state-check tasks should have deterministic ground-truth checks. Use Luna for semantic cases and report judge-versus-deterministic agreement.

P1 · operations

Bound retries and cooldowns

Predeclare zero or one site-block retry after a fixed cooldown. Retried cells stay flagged. Unbounded challenge recovery creates model-dependent runtime and policy drift.

P2 · metrics

Normalize efficiency carefully

Compare time and harness calls only among eligible completed cells. Keep vendor-specific token schemas separate; do not add unlike token fields into one score.

P2 · provenance

Capture runtime-resolved identity

Store the model reported by CLI runtime events where available, in addition to the requested model and effort already present in the manifest.

P2 · statistics

Report paired uncertainty

Use task-level paired bootstrap intervals and an exact paired test. Show excluded tasks separately; never impute them as ordinary failures or retain their clean cells in a capability claim.

Do not immediately rerun the same live task from the same IP. The pilot suggests site-defense state persists across tightly spaced arms. A rerun without cooldown or isolated egress would mostly measure Cloudflare state.

Go/no-go gates for publication

  • Replication: at least 3 repeats per task/harness/model cell.
  • Comparable coverage: at least 80% of selected tasks remain in the scored set.
  • Blocking: CAPTCHA task-exclusion rate at or below 10%, with no within-pair order gap above 15 percentage points.
  • Reliability: judge errors 0%; technical failures below 5%; no leaked browser or daemon processes.
  • Judge calibration: at least 95% agreement with deterministic graders on tasks that support them.
  • Reporting: scored tasks, excluded tasks, raw audit outcomes, order diagnostics, eligible latency, and uncertainty all shown separately.
